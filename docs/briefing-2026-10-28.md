> 팀원이 정리한 노션 "온라인 설명회 타임라인별 내용 요약"(영상: https://www.youtube.com/live/utX9C3GsTRA)을 읽고, 이 프로젝트에 해당하는 것만 옮겼다. 괄호 안은 영상 시간.

## 새로 확인된 것과 우리 상태

| 설명회 내용 | DriveLog |
|---|---|
| 개발 단계에서는 SDK 권한 신청·승인 없이, 문서의 권한을 `AndroidManifest.xml`에 선언하면 쓸 수 있다 (43:41). Vehicle·NaviHelper·SpeechToText·TextToSpeech·FusedLocation 모두 해당 (49:24) | 맞음. Playground My Project에서 TextToSpeech가 "준비 중"으로 보여도 공모전에는 문제없다. 승인된 권한만 심사하는 것은 App Market에 실제로 올릴 때다 (44:11) |
| 외부 API와 외부 네트워크 연결을 써도 된다 (48:59) | 조직 서버(Supabase)·관리자 웹(Vercel)을 쓰는 구조 그대로 괜찮다 |
| 2차 PT에서 실차 시연은 없고, Playground 에뮬레이터로 검증한다 (32:15) | 시연은 에뮬레이터 + Virtual Console로 ([demo-script.md](demo-script.md)) |
| 시뮬레이션: Virtual Console에서 기어·문·배터리를 바꾸고 앱이 SDK로 받아 반응하는지 보여 준다 (45:43~46:28) | 시연 흐름이 정확히 이것: 기어 D → 계기판 거리 → P → 분류 화면 |
| 생성형 AI 도구는 써도 되지만, 참가자가 앱 전체 구조와 로직을 이해하고 **2차 PT 기술 질의응답에서 직접 설명**해야 한다 (31:40) | ⏳ 팀이 구조를 설명할 수 있게 준비 필요 (아래 "할 일") |
| SDK를 많이 쓰는 것 자체가 목적이 아니다. 고객 문제에 필요한 SDK를 고르고 핵심 기능에서의 역할을 보여 줘라 (43:13) | 기술 활용성 설명을 "SDK 개수"가 아니라 "운행기록부의 어느 칸을 어느 API가 채우는가"로 한다 ([sdk-usage.md](sdk-usage.md)) |
| 처음부터 다 만들지 말고 핵심 사용자 가치 한 가지를 실제 동작으로 보여 줘라 (47:44) | 핵심 가치: "운전만 하면 운행기록부가 채워지고, 정차 후 한 번만 누른다" |
| 기획서는 ① 어떤 사용자의 어떤 문제 ② 필요한 차량 정보·기능과 목적 ③ 어떤 SDK·API로 어떻게 구현·테스트 순서로 (37:55~38:22) | [plan-summary.md](plan-summary.md)의 심사 항목별 문장·SDK 활용표·개발 계획이 이 순서를 담고 있다 |
| 차량을 업무 공간으로 쓰는 고객도 소개함. 다만 기업용 서비스를 우선 평가한다는 말은 없음 | 사업성 설명은 고객(법인·개인사업자의 업무용 차량)과 지속 사용 이유(매달 쓰는 법정 서식)로 |
| 미공개 SDK도 제공할 예정 (37:02), ADAS·차량 제어는 시점·범위 미확정 | 지금 쓰지 않음. 나오면 다시 검토 |

## 할 일

- **PT 기술 질의응답 준비**: AI 도구로 만든 코드라도 팀이 구조·로직을 설명해야 한다. 운행 감지(기어 → 상태 머신), 해시 체인, 동기화·서버 권한(RLS), 암호화, 음성 안내가 각각 어떻게 동작하는지 설명할 수 있어야 한다.
- 시연 영상(가산점)은 에뮬레이터 화면 녹화로 ([demo-script.md](demo-script.md)).
- 심사용 계정이 공지되면 Collaborator 초대 후 접근 확인.
